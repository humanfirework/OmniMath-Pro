# 手写渲染选型与实测：Canvas 2D / GPUI / 原生壳

> 目标：在不牺牲三端（桌面、安卓手机、安卓平板）的前提下，把手写输入到上屏的延迟压到 1 帧左右，并给出何时才值得替换渲染层的判定标准。

## 1. 实测方法与结果

测量对象是当前白板引擎 `src/lib/ink/engine.ts`：Pointer Events → `getCoalescedEvents()` → 世界坐标 → 增量重绘 → 下一帧。

- 环境：Chromium 151 headless，Linux，1440×900，60Hz 虚拟刷新；合成鼠标事件（非真实触控笔）。
- 样本：连续 6 条长笔迹、约 720 个 pointermove，引擎探针保留最近 240 个样本。
- 指标：事件 `timeStamp` → 下一个 `requestAnimationFrame` 的时间差（引擎内 `sampleLatency`）。

| 指标 | 数值 |
| --- | --- |
| 平均 | 9.8 ms |
| P95 | 17.9 ms |
| 最大 | 57.5 ms |
| 样本数 | 240 |

9.8 ms 约等于 60Hz 下 0.6 帧，P95 约 1 帧；最大值出现在合成事件批量涌入 + React 状态更新的瞬间，属于尖刺而非稳态。

复现：白板 → 右上「形状 / 像素 / 背景 / 清空」→「笔迹延迟测试」，在真实触控笔上书写，HUD 实时显示平均 / P95 / 最大。

## 2. 这些数字说明什么

- 稳态瓶颈不在 2D 光栅化。当前笔迹是**矢量轮廓填充**（`buildInkOutline`），每帧只增量绘制新段（`drawLiveIncrement`），单帧成本很低。
- 主要成本是**事件到帧的调度**：浏览器在 vsync 边界合成，Pointer Events 到上屏至少 1 帧；60Hz 下理论下限约 16.7 ms 的往返，探针测的是「事件→下一帧开始」，因此 9.8 ms 已接近该路径的下限。
- 真实触控笔的体验还叠加：屏幕采样率（120Hz 平板为 8.3ms/帧）、Android 输入链路、以及笔尖到玻璃的物理距离。这些不是 Canvas 与 GPUI 的差异能解决的。

## 3. Canvas 2D vs GPUI

| 维度 | Canvas 2D + Tauri 2（当前） | GPUI（Zed 的 Rust UI 框架） |
| --- | --- | --- |
| 三端覆盖 | Web / PWA / Tauri 桌面 / Tauri 2 Android | 以桌面为主，Android 不是其支持目标 |
| 手写路径 | Pointer Events + 增量 Canvas，实测 9.8ms 平均 | 需自建路径网格化 + GPU 绘制，触摸/IME 链路要自己接 |
| 2D 绘制性能 | 中等笔迹量下远低于一帧预算；GPU 加速由浏览器合成器负责 | 极高上限，适合十万级图元与复杂动效 |
| 3D | three.js / WebGL，按需加载 | 可用 wgpu，但要重写渲染与交互层 |
| 内存 / 启动 | WebView 常驻，Tauri 桌面安装包小；首屏已按 chunk 拆分 | 无 WebView，内存更可控，但需重写全部 UI 与组件 |
| 生态与迭代速度 | React + Radix + CodeMirror + mathjs，迭代快 | 全 Rust 重写，现有 80 个测试文件与组件全部作废 |
| 风险 | 长笔迹/超大画布需继续做分块与剔除（已做视口剔除） | 框架年轻、API 变动快；移动端缺失直接违背三端目标 |

结论：**GPUI 解决的是「桌面窗口与大规模 GPU 场景」的性能上限，不解决手写输入链路的下限，也无法覆盖安卓。** 当前 9.8ms / P95 17.9ms 已接近 60Hz 的事件→帧下限，换 GPUI 不会把 1 帧变成 0 帧，却会丢掉 Web、PWA、Android 与全部现有组件。

## 4. 什么时候才需要换渲染层

在**安卓平板真机**上用「笔迹延迟测试」采集，满足任一条件再启动替换评估：

1. P95 > 25 ms，且连续书写 30 秒后 P95 继续上升（说明不是单帧尖刺，而是重绘/GC 累积）。
2. 单页笔迹 > 5,000 条时，平移/缩放帧率低于 50fps。
3. 120Hz 设备上平均延迟 > 2 帧（>16.7ms）。

按成本从低到高的缓解顺序：

1. 已做：`getCoalescedEvents()` 合并采样、增量重绘、视口剔除、按需重绘。
2. 笔迹预测：用最后两点速度外推 1 帧，画在独立预测层，下一帧真实点时清除。预计再省 0.5–1 帧，但需要真机调参避免「尾巴过冲」。
3. OffscreenCanvas + Worker：把主画布光栅化移出主线程，避免 React 更新干扰。
4. 分块（tile）缓存：超大画布只重绘脏块，配合位图缓存。
5. 最后才是原生渲染器（GPUI/wgpu）；到这一步再评估是否值得放弃 Web 与 Android 覆盖。

## 5. 与 Apple 备忘录的差距在哪里

Apple 备忘录的跟手来自三件事，而不是某个 UI 框架：PencilKit 的**预测笔迹**、120Hz ProMotion、以及系统级输入优先级。我们能复刻的是前两项中的预测与高刷适配；第三项取决于 Android 设备与 Tauri WebView 的输入链路，需要在真机上量。当前引擎已具备压力感应、合并事件、增量绘制，缺的是预测层与真机数据。

## 6. 当前决策

- 保留 **Canvas 2D 手写引擎 + Tauri 2 外壳**；3D 继续用 three.js/WebGL 独立渲染，互不拖累。
- 不整体迁移 GPUI；把「是否需要原生渲染」交给第 4 节的阈值和真机数据决定。
- 下一步优先级：真机延迟采集 > 预测层 > 分块缓存 > 渲染层替换。
